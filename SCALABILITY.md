# SCALABILITY — persistence, memory, and archive

This is a decision record for how the software handles data on disk and in memory. It pairs with `ARCHITECTURE.md` (engineering layout) and is written so the question is not re-argued without cause. Every figure in it is either derived in the document or measured on one of the two shipped example projects, and says which.

**Decision in one line:** xlsx stays for inputs; **parquet for arrays plus JSON for metadata** is the per-run state cache; the Stage 3 schedule simulation runs in chunks (batches of iterations) in numpy. **No database backend** at any foreseeable project scale.

---

## 1. Data sizes — measured

The two shipped projects are `synthetic_wind` and `synthetic_road`. Their inputs are in `tests/fixtures/`.

| Quantity | `synthetic_wind` | `synthetic_road` | How it is obtained |
|---|---|---|---|
| Activities in the schedule | 171 | 34 | Count of `TASK` rows in `wind_schedule.xer` and `road_schedule.xer` |
| Register workbook | about 48 kB | about 43 kB | File size of `wind_register.xlsx` and `road_register.xlsx`, rounded: the registers are regenerated by script, and a regeneration moves the size by a few bytes |
| Schedule export (`.xer`) | about 39 kB | about 8 kB | File size of `wind_schedule.xer` and `road_schedule.xer`, rounded for the same reason |
| Iterations in a production run | 100,000 | 100,000 | The canonical production count (`docs/SOFTWARE_USER_GUIDE.md` §3.3) |
| Stage 3 batch size | 2,000 | 2,000 | `STAGE3_BATCH_SIZE` in `stage3_config.py` |

### The working set of one batch

One call of the schedule kernel (`run_batch` in `cpm_kernel.py`) holds five `(batch, activities)` arrays in the working precision (early start, early finish, late start, late finish, slack), one `(batch, activities)` boolean array (critical-path membership, 1 byte per element), and a `(batch,)` vector of project finishes. So:

> working set ≈ batch × activities × (5 × bytes per number + 1)

with 4 bytes per number in `float32`, the default, and 8 in `float64`, which is opt-in. This was checked by running `run_batch` on both shipped schedules under `tracemalloc` (random durations; measured peak against the formula, in MB):

| Project | Precision | Batch | Formula | Measured peak |
|---|---|---|---|---|
| `synthetic_wind` | float32 | 2,000 | 7.18 | 7.21 |
| `synthetic_wind` | float32 | 10,000 | 35.91 | 35.96 |
| `synthetic_wind` | float64 | 2,000 | 14.02 | 14.04 |
| `synthetic_road` | float32 | 2,000 | 1.43 | 1.44 |
| `synthetic_road` | float64 | 2,000 | 2.79 | 2.80 |

The formula is within one percent of the measurement in every case (the largest gap, on the smaller project, is 0.6%), so it is used below to size a run.

### The same arithmetic with no batching

If the whole run were held at once (batch = 100,000 iterations), the formula gives, for `float32` and `float64`:

| Project | float32 | float64 |
|---|---|---|
| `synthetic_wind` (171 activities) | 100,000 × 171 × 21 bytes ≈ 359 MB | 100,000 × 171 × 41 bytes ≈ 701 MB |
| `synthetic_road` (34 activities) | 100,000 × 34 × 21 bytes ≈ 71 MB | 100,000 × 34 × 41 bytes ≈ 139 MB |

To size your own schedule, put your activity count and your iteration count (or batch size) into the formula. As an illustration only, a hypothetical schedule of 2,000 activities, unbatched at 100,000 iterations, would need 100,000 × 2,000 × 21 bytes ≈ 4.2 GB in `float32` (≈ 8.2 GB in `float64`); at a batch of 2,000 it needs 2,000 × 2,000 × 21 bytes ≈ 84 MB. That difference is the reason for chunking (§3.3).

### What is not stated here

The size of a run's state cache on disk, and of the HTML and Word deliverables, depend on the project and the iteration count and have not been measured for the shipped projects in this document, so none is quoted. Measure them by looking at `outputs/runs/<date>_<binding key>/` after a run.

## 2. Where a database would and wouldn't help

A database earns its keep when one of these is true. Assessment for this software:

| Database benefit | Applicable? |
|---|---|
| Multiple users / concurrent writes | No. Single analyst, sequential workflow |
| Data larger than RAM, needs streaming | No. The working set of a batch is megabytes for the shipped projects (§1), and for a larger schedule it is bounded by the batch size, which is **chunking** the iteration loop, not query offloading |
| Random access into individual rows of a very large table | No. Analytics consume whole arrays via `np.percentile`, `np.mean`, etc. Columnar reads of a parquet file deliver the same with less ceremony |
| Transactions / ACID guarantees | No. Each run is a single atomic produce-and-archive |
| Cross-run analytics over a long history | Marginal. One run per reporting period; flat parquet plus an index file gives the same value with less complexity |
| Schema enforcement | Already enforced in code (dataclasses + `RiskInput` / `IntegratedConfig` / `SimRawResults`). A database would only enforce what is already enforced |

A database would **not** help with:

- The xlsx inputs — these are the canonical interchange format with the planner and the register owner; that won't change
- The per-run numpy arrays during a run — they live in RAM as numpy buffers, not in any persistent store
- Reproducibility — git, the seed and locked input paths already give that

**Postgres / MySQL / SQL Server are not warranted at any foreseeable scale.** Single analyst, no concurrent writes, no transactional needs. Adding a server-based database introduces operational burden (backups, schema migration, connection pooling) for no benefit.

## 3. The right tool at each layer

### 3.1 Inputs — xlsx stays

The risk register, the schedule export and the strawman methodology workbook are owned by other parties (the planner, the register owner). xlsx is the canonical interchange format and any move away breaks the interchange. Header-driven readers (`v5_register_reader.py`, `strawman_reader.py`, `p6_reader.py`) already tolerate column reordering and added columns; that is the right level of robustness for the inputs.

### 3.2 Per-run state cache — parquet for arrays + JSON for metadata

The per-run state cache is written by `write_state_cache` in `state_cache.py` and read back by `read_state_cache`. It replaces an earlier single-file pickle.

Why not pickle:

- Pickle is fragile across Python versions, class-definition changes, and library upgrades
- Pickle is not language-portable; if anyone wants to read these from R, Excel, or BI tools, pickle is a dead end
- Parquet is schema-stable and columnar, written snappy-compressed here, and is read natively by pandas, R, Spark, DuckDB, Polars
- JSON beside it for the small metadata dict (run date, seed, paths, hashes, P-level summary, engine versions, cross-validation status) is readable in any text editor and easy to diff across runs

The layout of a run's directory:

```
outputs/runs/<date>_<binding key>/
  <array>.parquet                 # one file per cached array (1-D: one column "value"; 2-D: one column per position)
  metadata.json                   # the cache's structure, each array replaced by a reference; the gate's full text
  manifest.json                   # array name -> where it sits in the structure, with dtype and shape
  provenance.json                 # what makes the run evidence
```

The diagnostic (`scripts/run_diagnostic.py`) loads from this directory, and the deliverable writes the one-page diagnostic itself on every run; it replaced a separate, earlier diagnostic script. The parquet dependency, `pyarrow>=15`, is in `requirements_client.txt`.

### 3.3 Stage 3 in-memory data — chunked iteration in numpy, not a DB

Held whole, a Stage 3 run's buffers grow with iterations × activities (§1). The fix is operational, not architectural: the iteration loop runs in batches, and only aggregates are kept between them.

**How it is built.** The kernel `run_batch` in `cpm_kernel.py` works on one batch and keeps no state between calls; it does not loop over batches itself. The orchestrator in `cpm_simulation.py` does the looping, driven by `ScheduleMCConfig.batch_size` (default 10,000; Stage 3 production sets 2,000 through `STAGE3_BATCH_SIZE`). Between batches it keeps only what the analysis needs: the project-finish samples, and per-activity criticality and float aggregates accumulated by `accumulate_batch_stats`. The per-batch arrays are then discarded.

Peak memory is therefore set by the batch size and the activity count, not by the iteration count, and the iteration count only changes how many batches run.

**Float32 is the default precision.** Single precision is sufficient for duration arithmetic, and the critical-path test (`slack <= CRITICAL_PATH_TOL`) carries a tolerance for the rounding that accumulates across the topological pass. Float64 is available per call (`precision="float64"`) for diagnostic runs; it doubles the per-number cost, which is the 5 × 8 + 1 against 5 × 4 + 1 in the formula in §1.

**Per-iteration early and late dates** are not stored beyond the batch, since downstream analytics need only the project-finish distribution and the criticality aggregates. If a particular analysis needs them (e.g. activity-level percentiles), save only that activity's column to parquet during the batch loop, not the whole `(iterations × activities)` matrix.

### 3.4 Cross-run archive — a directory of run directories; a manifest CSV is a design, not built

Each run's directory (§3.2) is already self-contained, so a cross-run archive is just a directory of those directories, plus an index if one is wanted. **No cross-run `outputs/runs/manifest.csv` is written by the software today**; the shape below is the design for anyone who wants one.

```
outputs/runs/
  manifest.csv                     # one row per run
  <date>_<binding key>/
  <date>_<binding key>/
  ...
```

The columns such an index would carry: `run_date`, `mode`, `register_version`, `register_sha256`, `p6_version`, `strawman_version`, `seed`, `iterations`, `cost_p80`, `schedule_p80_days`, `integrated_p80`, `cv_all_pass`, `engine_versions`, `notes`.

Pandas reads such an index in one line and joins it to the per-run parquets when cross-run analysis is wanted.

### 3.5 If cross-run queries become routine — DuckDB, not Postgres

If someone is asking weekly-cadence cross-run questions ("show me the top three schedule risks across all register revisions", "how has the cost-vs-schedule diversification benefit moved over the project lifecycle"), introduce **DuckDB** rather than a server-based database:

- Embedded — no server, no daemon, no operational burden
- Reads parquet directly without ingestion: `SELECT * FROM 'outputs/runs/*/<array>.parquet'` works as-is, for any one array name
- Supports SQL joins across multiple parquet files in a directory, including views over an index file
- Native Python integration: `duckdb.connect()` then `con.execute(sql).fetch_df()`
- Adds no friction for the parquet archive — DuckDB queries existing files in place

Decision criterion for adopting DuckDB: when an analyst is writing pandas across-run join code three weeks in a row to answer the same shape of question, that is the trigger. Not before.

## 4. Migration sequence

The order in which these decisions were taken, and where each stands:

1. **Replace the pickle state cache with parquet + JSON — done.** `state_cache.py` writes and reads it; `pyarrow>=15` is in the requirements. The pickle fixture is no longer held in the tree.
2. **Chunked iteration in the schedule kernel — done.** The kernel exposes `run_batch`, and `cpm_simulation.py` orchestrates the batches.
3. **A cross-run `outputs/runs/manifest.csv` updater — not built.** It would be written at the close of a run, so that the archive accumulates organically (§3.4).
4. **Optional, only if cross-run queries become routine:** add DuckDB and an `analytics/` directory of `.sql` files querying `outputs/runs/*/*.parquet`.
5. **Never:** introduce Postgres or any server-based database.

Steps 1 and 2 are in the product; step 3 is unbuilt; step 4 is on-demand; step 5 is a non-decision.

## 6. Decisions recorded

The following are recorded so they are not re-opened without cause:

- **Inputs stay xlsx.** Canonical interchange with external parties; not negotiable
- **Per-run state is parquet + JSON.** Pickle is retired
- **Stage 3 uses chunked iteration in numpy.** Float32 default; float64 as opt-in
- **The cross-run archive is flat parquet directories, with an index file if wanted.** No server-based database, no embedded database, until cross-run queries become routine
- **DuckDB is the only database option ever considered**, and only as a query layer over existing parquet files. Postgres / MySQL / SQL Server are out of scope at any project size

If any of these need to change, the change is a deliberate, reviewed one — it does not happen by drift.
